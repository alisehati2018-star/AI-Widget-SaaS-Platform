# تحلیل کامل سیستم — صفحه‌به‌صفحه، هر دو پنل + عمومی، با امتیازدهی

تاریخ: ۱۴۰۵/۰۴/۲۳ · شاخه: `claude/gallant-shannon-8b31td` · دامنه: **۵۳ صفحه** (۲۴ ادمین + ۱۶ داشبورد فروشنده + ۱۳ عمومی/احراز) + بک‌اند پشتیبان هر صفحه

روش: بازخوانی فایل‌به‌فایل کد هر صفحه + تطبیق هر عمل با endpoint بک‌اند + اسکن خودکار ضدالگوها (خطای بلعیده‌شده، موفقیت دروغین، اسپینر بی‌نهایت، حذف بدون تایید) + نتایج تایید زندهٔ قبلی (استک واقعی PG/Redis/uvicorn/بیلد Next + سه جاروی مرورگری Chromium). این گزارش **فقط تحلیل** است — هیچ کدی در این نوبت تغییر نکرده تا شما اول بررسی کنید.

## ۵) بک‌اند پشتیبان صفحات — ۹.۶

- **تایید زنده** (استک واقعی): همهٔ endpointهای هر دو پنل ۲۰۰؛ چرخهٔ کامل AI (قالب→کشف→ایمپورت→زنجیره→اهلیت→failover)؛ **مسیر پول توکن-دقیق** (COGS=$0.00162 → ۲۲٫۶۸ کردیت با حاشیهٔ ۴۰٪ → کیف پول → finance/سود)؛ کش L1 تکرار مجانی؛ degrade تمیز.
- امنیت (گزارش‌های قبلی): PBKDF2، JWT چرخشی، TOTP+replay-guard، CSRF، سه‌لایه rate-limit، ایزولاسیون tenant اجباری در query-builder، کلیدها هش، CSP — همه پابرجا.
- ساختار: ۱۵۴ فایل، صفر فایل بالای ۴۰۰ خط (گیت CI)؛ ۱۸۷ تست سبز.
- کسری ۰٫۴: پوشش integration فقط با ES/سرور واقعی اجراشدنی است + دو endpoint یتیم کم‌اهمیت (`/admin/zero-results` مستقیم، `/admin/tenants/{id}/keys` جدا) که صفحات از مسیرهای دیگر همان داده را می‌گیرند.

## ۶) تحلیل نهایی ضعف‌ها و کمبودها (اولویت‌بندی برای تصمیم شما)

### دستهٔ الف — قابل رفع در کد، پیشنهاد: فوری (همهٔ ۱۳ یافتهٔ بخش ۳)
تمرکز ۱۰۰٪ در داشبورد فروشنده. سه زیر-الگو: (۱) موفقیت/حالت دروغین D3/D4، (۲) عمل مخرب بدون confirm D7/D8، (۳) شکست بی‌پیام/اسپینر بی‌نهایت بقیه. تا رفع نشوند، تجربهٔ فروشنده همان «حس نمایشی بودن» را در لحظات خطا می‌دهد که در ادمین ریشه‌کن شد.

### دستهٔ ب — وابسته به محیط شما (کد آماده است)
1. **Elasticsearch واقعی** → چرخهٔ کامل RAG، KPIهای جست‌وجو، صفحات ES-محور با دادهٔ واقعی (sandbox اجازهٔ نصب ES نداد).
2. **کلید واقعی ارائه‌دهنده (OpenRouter)** → جایگزینی مستقیم؛ مسیر با قرارداد یکسان زنده تایید شده.
3. **Merchant زرین‌پال** → تراکنش sandbox واقعی.
4. **پیمایش دستی موبایل** روی دستگاه واقعی (جاروی خودکار ۳ عرض پاس شده).

### دستهٔ ج — معماری/آینده (v2، مسدودکننده نیست)
1. HA چندسرور (تک‌سرور فعلی مستند در runbook).
2. rerank اپ‌ساید فقط عنوان محصول را به reranker می‌دهد (توضیحات را نه) — بهبود کیفیت، نه باگ.
3. `Reranker` تک‌URL قدیمی بدون مصرف‌کننده مانده (مستند به‌عنوان legacy؛ کاندید حذف).
4. audit trail داشبورد فروشنده خطا را از «خالی» تفکیک نمی‌کند (D13، جزئی).

### چیزی که بررسی شد و مشکلی نداشت
mock/داده‌ی ساختگی (صفر)، endpoint بدون مصرف‌کننده در AI (صفر)، کنترل UI بی‌اثر (صفر — آخرین مورد rerank بود که سیم‌کشی شد)، i18n (صفر خطا)، بیلد کامل (سبز)، تزریق SQL/XSS/CSRF (پاک)، حجم فایل‌ها (صفر تخلف).

## ۸) وضعیت رفع (به‌روزرسانی)

**هر ۱۳ یافتهٔ D1–D13 رفع شد** + ۹ مورد هم‌خانوادهٔ دیگر که در جاروی کامل پیدا شد:

|---|---|
| D1/D2 (team) | catch + Alert سطح صفحه + `disabled={busy}` روی دکمه‌های ردیف |
| D3 (leads) | optimistic با **rollback** روی شکست + Alert |
| D4 (settings tracking) | optimistic با rollback + پیام موفقیت فقط بعد از تایید سرور |
| D5 (export) | try/catch + پیام `exportFailed` (settings و leads) |
| D6 (widget saves) | catch + Alert خطا |
| D7 (keys revoke) | `window.confirm` با نام کلید + catch + busy |
| D8 (knowledge delete) | `window.confirm` با عنوان مقاله + catch + busy |
| D9 (credits) | مصرف `error`/`reload` از hook + دکمهٔ «تلاش مجدد» |
| D10 (assistant status) | حالت شکست + retry؛ ذخیرهٔ greeting هم catch گرفت |
| D11 (catalog sync) | حالت شکست + retry؛ ذخیرهٔ connection هم catch گرفت |
| D12 (onboarding resend) | موفقیت فقط بعد از سرور؛ خطا Alert؛ شکست پروفایل → retry به‌جای اسپینر ابدی |

### موارد «دستهٔ ج» که بسته شد (به‌روزرسانی دوم)
- **کیفیت rerank:** ورودی cross-encoder حالا عنوان + توضیحات (سقف ۳۰۰ نویسه) است، نه فقط عنوان — با تست.
- **کلاس legacy `Reranker`** (بدون مصرف‌کننده) حذف شد؛ `ChainedReranker` تنها مسیر است.
- **هشدارهای i18n صفر شد** (۹۷ ← ۰): چکر حالا hookهای scoped (`useTranslations("admin.aiConfigPage")` با aliasهای `ta`/`tp`/`tm`)، کلیدهای template-literal (`type_${x}`) و کلیدهای map-driven را می‌فهمد؛ ۱۶ کلید واقعاً مردهٔ `models.*` از هر دو زبان حذف شد.

## ۹) مدیریت خطا سرتاسری + تست سلامت کامل (به‌روزرسانی سوم)

### الف) خطاها — از سرور تا چشم کاربر
- **backend:** هر خطای خروجی API حالا قالب استاندارد `{code, message, request_id}` دارد — شامل خطاهای اعتبارسنجی FastAPI (قبلاً `{"detail":[...]}` خام برمی‌گشت ← حالا `validation_error` با خلاصهٔ فیلد) و خطاهای framework مثل 404/405 (کدهای پایدار `not_found`/`method_not_allowed`). تایید زنده شد.
- **frontend:** تا امروز همهٔ catchها **پیام خام انگلیسی سرور** را نشان می‌دادند. حالا hook مشترک `useApiErrorMessage` هر ۳۹ کد خطای backend را به پیام فارسی/انگلیسی بومی نگاشت می‌کند (`errors.codes.*` در هر دو زبان) و ۷۲ نقطهٔ catch در ۴۴ فایل به الگوی `apiMsg(err) ?? fallbackِ همان بخش` مهاجرت کردند — یعنی هر بخش، خطای بومیِ مخصوص خودش را نشان می‌دهد و کد ناشناخته به پیام سرور و بعد fallback بخش برمی‌گردد.

### ب) تست سلامت کامل سیستم
- **`GET /admin/health/deep`** (جدید): همهٔ زیرسیستم‌ها هم‌زمان probe می‌شوند — PostgreSQL (+ سنجش این‌که migrationها عقب نیستند)، Redis، Elasticsearch، صف Celery (پاسخ زندهٔ workerها)، زنجیرهٔ AI (تعداد endpoint فعال هر task + وضعیت failover) — به‌علاوهٔ وضعیت پیکربندی درگاه پرداخت و ایمیل. هر جزء: وضعیت/تأخیر/جزئیات خطا؛ هیچ probeای نمی‌تواند endpoint را بیندازد.
- **کارت «سلامت عمیق» در /admin/health** (جدید): جدول هر ۷ جزء با برچسب فارسی، تأخیر و جزئیات + دکمهٔ بررسی دوباره.
- **`scripts/system_health.py`** (جدید): CLI اپراتور — جدول متنی + exit code (۰=سالم، ۱=degraded، ۲=قطع) برای cron/مانیتورینگ.
- **اجرای زنده:** postgres ✅ (migrations=0020) · redis ✅ · queue ✅ (۱ worker) · ai_registry ✅ (chat=1, rerank=1) · elasticsearch ❌ «not reachable» (در sandbox نصب‌شدنی نیست — و دقیقاً همین را گزارش می‌دهد) · psp/email = پیکربندی‌نشده (اطلاع‌رسانی، نه خطا).
- **۸ تست جدید backend** (envelope اعتبارسنجی/404/405 + aggregation و degrade و احراز deep-health) → مجموع ۱۹۵ سبز.

گیت‌ها پس از همهٔ این تغییرات: ruff/mypy/pytest سبز، tsc پاک، i18n صفر/صفر، hardcoded و size صفر، `next build` سبز، و هر سه جاروی مرورگری (a11y/responsive/functional) صفر شکست.
