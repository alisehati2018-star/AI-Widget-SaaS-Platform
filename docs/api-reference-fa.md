# مرجع کامل API ویترین (ACIP) — احراز هویت، امنیت، ایندکس محصول و سفارش

این سند مرجع فنیِ کاملِ API عمومی ویترین است: چطور با کلید متصل شویم، چه
تضمین‌های امنیتی وجود دارد، و دقیقاً چطور هر **محصول** و هر **سفارش** در
Elasticsearch ایجاد/به‌روزرسانی/حذف می‌شود. برای راهنمای نصب گام‌به‌گام
ماژول‌های OpenCart 3 و وردپرس، به [`integrations-fa.md`](integrations-fa.md)
مراجعه کنید؛ کد منبع دو ماژول در [`/plugins`](../plugins/README.md) است.

---

## ۱) احراز هویت و امنیت

### ۱.۱) کلید API و ارتباط آن با پلن مشتری

هر درخواست با هدر `x-api-key` احراز هویت می‌شود. کلیدها از داشبورد ویترین در
**داشبورد → کلیدهای API** (`/dashboard/keys`) ساخته می‌شوند — همان صفحه‌ای که
سایر بخش‌های پلتفرم از آن استفاده می‌کنند، بنابراین:

* هر کلید به‌طور دائمی به **همان tenant** (فروشگاه) صاحبِ حساب متصل است؛ کلید
  هرگز نمی‌تواند داده‌های فروشگاه دیگری را بخواند یا بنویسد (ایزوله‌سازی سخت —
  رجوع کنید به §۴).
* مصرف هر کلید (تعداد جست‌وجو، پیام دستیار، حجم ایندکس) از **اعتبار/پلن همان
  tenant** کسر می‌شود — یعنی امنیت و مدل مصرف هر دو مستقیماً به پلن مشتری در
  همین سایت گره خورده‌اند، نه یک سیستم احراز هویت جدا.
* کلیدها به‌صورت **هش‌شده** (SHA-256) در پایگاه‌داده نگه‌داری می‌شوند؛ مقدار خام
  فقط یک‌بار، در لحظهٔ ساخت، نمایش داده می‌شود.
* کلید هر زمان از همان صفحه **باطل (revoke)** می‌شود و بلافاصله از کار می‌افتد.

هر کلید یکی از سه دامنهٔ دسترسی (scope) را دارد — **کمترین سطح دسترسی لازم را
به هر مصرف‌کننده بدهید**:

| Scope | برای چه کسی | چه کاری مجاز است |
|---|---|---|
| `widget` | مرورگر خریدار (ویجت فروشگاه) | فقط `/v1/search`، `/v1/suggest`، `/v1/chat*` — امن برای افشا در کد سمت کاربر |
| `sync` | سرور فروشگاه (ماژول OpenCart/وردپرس) | فقط `/v1/sync/*` (محصول + سفارش، webhook و bulk) — هرگز نباید در مرورگر افشا شود |
| `admin` | فقط عملیات پلتفرم (اپراتور ویترین) | مسیرهای `/admin/*` |

یک کلید `widget` هرگز نمی‌تواند به `/v1/sync/*` بنویسد و برعکس — این چک در
سرور با `principal_allowed()` روی هر درخواست اجرا می‌شود، نه فقط در رابط
کاربری.

### ۱.۲) لایه‌های امنیتی

1. **TLS اجباری در تولید** — همیشه از `https://` استفاده کنید؛ کلید و بدنهٔ
   درخواست هرگز روی HTTP ساده ارسال نشوند.
2. **کلید = هویت + مجوز** — بدون `x-api-key` معتبر، پاسخ `401 unauthorized`
   است؛ با scope نامعتبر، پاسخ `403 forbidden` است.
3. **محدودیت نرخ per-tenant** — پیش‌فرض ۱۲۰ درخواست در دقیقه به ازای هر
   tenant (مستقل از نوع کلید)؛ عبور از آن `429 rate_limited` برمی‌گرداند. این
   حد در Redis شمارش می‌شود و در قطعی Redis به‌صورت «باز» (fail-open) عمل
   می‌کند تا هرگز کل فروشگاه را از کار نیندازد.
4. **ایزوله‌سازی سخت تننت (tenant isolation)** — هیچ کوئری‌ای بدون فیلتر
   `tenant_id` روی داده اجرا نمی‌شود؛ این یک عدم امکان معماری است، نه یک تنظیم
   قابل غیرفعال‌سازی (رجوع کنید به §۴).
5. **پاکت خطای یکسان** — هر پاسخ خطا شکل ثابت زیر را دارد تا ماژول‌ها بتوانند
   برنامه‌ریزی‌شده با آن رفتار کنند:
   ```json
   {"error": {"code": "invalid_request", "message": "...", "request_id": "..."}}
   ```
6. **امضای HMAC (اختیاری، برای اتصال‌های سفارشی/native webhook)** — پیاده‌سازی
   پایه (`Connector.verify_signature`) یک HMAC-SHA256 عمومی است و پیاده‌سازی
   WooCommerce با فرمت امضای بومی خودِ WooCommerce (`x-wc-webhook-signature`،
   HMAC-SHA256 با کدگذاری base64) سازگار است. دو ماژول رسمی ویترین
   (`/plugins`) خودشان مستقیماً و با `x-api-key` به API متصل می‌شوند، بنابراین
   امنیتشان کاملاً از طریق کلید scope-دار تأمین می‌شود؛ این هوک برای مواردی
   است که می‌خواهید webhook بومی خودِ CMS (بدون هدر کلید سفارشی) را مستقیماً
   به ACIP وصل کنید.

### ۱.۳) مدیریت کلید (برای مالک فروشگاه، از طریق نشست داشبورد)

| Endpoint | Method | توضیح |
|---|---|---|
| `/tenant/keys` | `GET` | فهرست کلیدهای فعلی (scope، برچسب، آخرین استفاده) |
| `/tenant/keys` | `POST` | ساخت کلید جدید؛ بدنه: `{"scope": "widget"\|"sync", "label": "..."}` |
| `/tenant/keys/{id}/revoke` | `POST` | باطل‌کردن فوری کلید |

این سه مسیر با نشست ورود مالک فروشگاه (کوکی/JWT داشبورد) کار می‌کنند، نه با
`x-api-key` — کلیدهای API را می‌سازند، مصرف نمی‌کنند.

## ۲) مرجع Endpointها

آدرس پایه: همان آدرسی که در تنظیمات ماژول به‌عنوان **آدرس API** وارد کرده‌اید
(مثلاً `https://api.acip.example`).

### ۲.۱) جست‌وجو و دستیار (کلید `widget`)

| Endpoint | Method | Scope |
|---|---|---|
| `/v1/search` | `POST` | `widget` |
| `/v1/suggest` | `GET` | `widget` |
| `/v1/chat` | `POST` | `widget` |
| `/v1/chat/stream` | `POST` | `widget` (پاسخ SSE) |

**درخواست جست‌وجو:**
```bash
curl -sS https://api.acip.example/v1/search \
  -H "x-api-key: acip_widget_xxx" -H "Content-Type: application/json" \
  -d '{"query": "گوشی سامسونگ", "size": 20, "filters": {"in_stock": true}}'
```
```json
{"results": [{"product_id": "42", "title": "گوشی سامسونگ گلکسی A54", "price": 189000, "score": 12.4}], "took_ms": 38}
```
فیلدهای بدنه: `query` (اجباری، ۱ تا ۵۰۰ کاراکتر)، `filters` (اختیاری، شیء
کلید-مقدار)، `size` (اختیاری، ۱ تا ۵۰).

**پیشنهاد خودکار:** `GET /v1/suggest?q=گوشی` → `{"suggestions": ["گوشی سامسونگ", ...]}`

**گفت‌وگوی دستیار:**
```bash
curl -sS https://api.acip.example/v1/chat \
  -H "x-api-key: acip_widget_xxx" -H "Content-Type: application/json" \
  -d '{"message": "بهترین گوشی زیر ۱۰ میلیون؟", "session_id": "s-1"}'
```
پاسخ شامل `answer` و `citations` (محصولاتی که پاسخ از آن‌ها استخراج شده) است.
`/v1/chat/stream` همان پاسخ را به‌صورت `text/event-stream` (رویدادهای `meta`،
جریان `data` توکن‌به‌توکن، و `done` با citations نهایی) برمی‌گرداند.

اگر خوشه Elasticsearch در دسترس نباشد، این مسیرها به‌جای خطای ۵۰۰، `503` با
کد پایدار (`search_unavailable`، `index_not_ready`، `assistant_unavailable`)
برمی‌گردانند — تخریب برنامه‌ریزی‌شده، نه شکست غیرمنتظره.

### ۲.۲) همگام‌سازی محصول (کلید `sync`)

| Endpoint | Method | توضیح |
|---|---|---|
| `/v1/sync/webhook?source={opencart\|woocommerce\|rest}` | `POST` | افزودن/ویرایش/حذف **یک محصول** (لحظه‌ای) |
| `/v1/sync/bulk` | `POST` | ورود اولیهٔ کاتالوگ (چند محصول یک‌جا) |

**Webhook محصول** — بدنه:
```json
{"event": "upsert", "product": {
  "product_id": "42", "name": "گوشی سامسونگ گلکسی A54",
  "description": "...", "manufacturer": "سامسونگ",
  "categories": ["موبایل", "سامسونگ"],
  "attributes": {"رنگ": "مشکی", "حافظه": "128 گیگابایت"},
  "price": 189000, "quantity": 12, "date_modified": "2026-07-01T10:00:00"
}}
```
برای حذف: `{"event": "delete", "product": {"product_id": "42"}}`.
شکل `product` بسته به `source` متفاوت است (فیلدهای OpenCart در مثال بالا؛
WooCommerce از `id`/`name`/`categories: [{"name": ...}]`/`attributes: [{"name","options"}]`/
`stock_status`/`date_modified` استفاده می‌کند). پاسخ موفق:
```json
{"status": "accepted", "product_id": "42", "type": "upsert"}
```
درخواست **پذیرفته** می‌شود و پردازش واقعی به‌صورت ناهمگام در صف کار انجام
می‌شود (idempotent — تکرار همان رویداد یا ترتیب نادرست هرگز ایندکس را خراب
نمی‌کند، چون نگارش با نسخهٔ خارجی مبتنی بر `date_modified` انجام می‌شود).

**Bulk محصول** — بدنه: `{"source": "opencart", "products": [ {...}, {...} ]}`
(حداکثر ۵۰۰۰ آیتم در هر درخواست). پاسخ: `{"status": "accepted", "count": N}`.

### ۲.۳) همگام‌سازی سفارش (کلید `sync`) — جدید

| Endpoint | Method | توضیح |
|---|---|---|
| `/v1/sync/order/webhook?source={opencart\|woocommerce\|rest}` | `POST` | افزودن/تغییرِ وضعیت **یک سفارش** (لحظه‌ای) |
| `/v1/sync/order/bulk` | `POST` | ورود اولیهٔ سوابق سفارش‌ها |

هر سفارش در ایندکس مجزای Elasticsearch با نام مستعار (alias) پیش‌فرض
`acip-orders` ذخیره می‌شود (قابل تغییر با متغیر محیطی `ORDERS_ALIAS`) — کاملاً
جدا از ایندکس کاتالوگ (`acip-products`)، اما با همان تضمین ایزوله‌سازی تننت.

**Webhook سفارش** — بدنه:
```json
{"event": "upsert", "order": {
  "order_id": "1007", "firstname": "علی", "lastname": "صحتی",
  "email": "ali@example.com", "total": 189000, "currency_code": "IRR",
  "order_status": "در حال پردازش",
  "date_added": "2026-07-01T09:00:00", "date_modified": "2026-07-01T09:00:00",
  "products": [{"product_id": "42", "name": "گوشی سامسونگ گلکسی A54", "quantity": 1, "price": 189000}]
}}
```
(شکل WooCommerce معادل: `id`, `status`, `billing: {email, first_name,
last_name}`, `line_items: [{product_id, name, quantity, price}]`, `total`,
`currency`, `date_created_gmt`, `date_modified_gmt`.)

نکتهٔ مهم دربارهٔ رویدادها: **تغییر وضعیت سفارش (لغو، مرجوعی، تکمیل و ...)
همیشه `upsert` است، نه `delete`** — سند سفارش در ایندکس می‌ماند و فقط فیلد
`status` به‌روز می‌شود، تا تحلیل/جست‌وجوی سفارش‌های لغوشده هم ممکن باشد.
`delete` فقط زمانی ارسال می‌شود که خودِ رکورد سفارش در فروشگاه (نه فقط
وضعیتش) پاک شود.

پاسخ موفق: `{"status": "accepted", "order_id": "1007", "type": "upsert"}`.

**Bulk سفارش** — بدنه: `{"source": "opencart", "orders": [ {...}, {...} ]}`
(حداکثر ۵۰۰۰ آیتم). پاسخ: `{"status": "accepted", "count": N}`.

**نگاشت داده در Elasticsearch** (`packages/acip_search/order_mapping.py`):

| فیلد | نوع | توضیح |
|---|---|---|
| `tenant_id` | keyword | فیلتر ایزوله‌سازی (اجباری روی هر کوئری) |
| `order_id` | keyword | شناسهٔ سفارش در فروشگاه مبدأ |
| `status` | keyword | وضعیت فعلی سفارش |
| `customer_email` / `customer_name` | keyword / text (fa) | اطلاعات مشتری |
| `items` | nested | `product_id`, `title`, `quantity`, `price` برای هر قلم |
| `total` | scaled_float | مبلغ کل |
| `currency` | keyword | واحد پول |
| `created_at` / `updated_at` | date | زمان‌بندی برای پرس‌وجوهای بازه‌ای |

سند با شناسهٔ قطعی `{tenant_id}:{order_id}` و نگارش خارجی مبتنی بر
`updated_at` نوشته می‌شود — دقیقاً همان الگوی idempotent محصول، پس ارسال دوباره
یا خارج از ترتیب هرگز داده را خراب نمی‌کند.

### ۲.۴) کدهای خطا

| کد | HTTP | معنی |
|---|---|---|
| `unauthorized` | 401 | کلید ارسال نشده یا نامعتبر/باطل‌شده |
| `forbidden` | 403 | کلید معتبر است ولی scope آن اجازهٔ این مسیر را نمی‌دهد |
| `rate_limited` | 429 | عبور از محدودیت نرخ تننت (۱۲۰ در دقیقه، پیش‌فرض) |
| `invalid_request` | 422 | بدنهٔ درخواست نامعتبر (فیلد گم‌شده/خارج از محدوده) |
| `search_unavailable` / `assistant_unavailable` | 503 | خوشهٔ Elasticsearch موقتاً در دسترس نیست |
| `index_not_ready` | 503 | ایندکس هنوز ساخته نشده (فروشگاه تازه متصل شده) |
| `internal_error` | 500 | خطای پیش‌بینی‌نشده (نادر؛ با `request_id` گزارش دهید) |

## ۳) چک‌لیست اتصال یک فروشگاه جدید

1. در **داشبورد → کلیدهای API**، یک کلید `widget` و یک کلید `sync` بسازید.
2. ماژول (OpenCart 3 یا وردپرس، از [`/plugins`](../plugins/README.md)) را نصب
   و در تنظیماتش آدرس API + همین دو کلید را وارد کنید؛ **آزمایش اتصال** را
   بزنید.
3. **ورود کامل کاتالوگ اکنون** را بزنید (`/v1/sync/bulk`) — ایندکس اولیهٔ
   محصولات ساخته می‌شود.
4. اگر همگام‌سازی سفارش را فعال کرده‌اید، **ورود کامل سوابق سفارش‌ها اکنون** را
   هم بزنید (`/v1/sync/order/bulk`).
5. از این پس هر افزودن/ویرایش/حذف محصول و هر افزودن/تغییر وضعیت سفارش
   به‌صورت لحظه‌ای پوش می‌شود؛ برای ترمیم رویدادهای ازدست‌رفته، چرخهٔ pull
   هر ۱۵ دقیقه اجرا می‌شود (رجوع کنید به [`integrations-fa.md`](integrations-fa.md) §۳).
6. ویجت جست‌وجو/دستیار را با کلید `widget` در فروشگاه فعال کنید (تزریق
   خودکار توسط هر دو ماژول انجام می‌شود؛ نیازی به ویرایش قالب نیست).

---

## ۴) ایزوله‌سازی تننت — چرا این یک قابلیت نیست، یک الزام معماری است

هر جست‌وجو، پیشنهاد، پاسخ دستیار، و نوشتن (محصول یا سفارش) از یک نقطهٔ واحد در
سرور عبور می‌کند که فیلتر `tenant_id` را **اجباراً** به کوئری/سند اضافه
می‌کند؛ کدی که بخواهد این فیلتر را دور بزند اصلاً کامپایل/اجرا نمی‌شود. کلید
API شما فقط `tenant_id` متعلق به خودتان را حمل می‌کند، پس حتی در صورت افشای
عمدی کلید `widget` (که ذاتاً کم‌خطر است)، امکان خواندن یا نوشتن داده‌های
فروشگاه دیگری وجود ندارد.
